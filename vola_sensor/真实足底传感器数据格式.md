# G1 双足 15 点 Hall 传感器数据格式

## 1. 先说结论

真实柔性磁感知足底直接提供的量只有：

- 左、右脚每脚 15 个 Hall 点；
- 每个点的 `Bx、By、Bz` 原始计数；
- 每个点的温度；
- 主机接收时间、有效位、数据年龄和实测采样周期。

真实传感器不直接输出法向力、切向力、压力、摩擦系数或接触点。基线差分、温漂补偿、滤波和归一化仍然只是磁场信号预处理，不能把数据名称改成力。

## 2. 左右脚身份和通道顺序

| 脚 | BLE 名称 | BLE 地址 | 采集适配器 | 数组索引 |
|---|---|---|---|---:|
| 左脚 | `left` | `98:A3:16:A1:BF:CA` | `hci0` | 0 |
| 右脚 | `right` | `98:A3:16:A1:C1:2E` | `hci1` | 1 |

实时数组顺序固定为：

```text
[left, right] -> [P00, P01, ..., P14] -> [Bx, By, Bz]
```

每脚 15 点的编号顺序为从脚尖到脚跟，每组十字形都是“上、左、中、右、下”：

```text
前掌:              P00
              P01  P02  P03
                   P04

中足:              P05
              P06  P07  P08
                   P09

后跟:              P10
              P11  P12  P13
                   P14
```

当前配置是临时直通映射 `BLE channel 0..14 -> P00..P14`。必须在 PCB 最终装配后，用单点磁场扰动实验确认通道顺序和每个芯片的 XYZ 正负号；不能仅根据左右对称猜测。

## 3. 单脚 BLE 原始帧：125 bytes

### 3.1 链路常量

| 项目 | 值 |
|---|---|
| Notify characteristic | `0000ab01-0000-1000-8000-00805f9b34fb` |
| 帧长 | 125 bytes |
| 字节序 | 每通道为大端 `>hhhh` |
| 通道数 | 15 |
| 每通道长度 | 8 bytes |
| 已知采样速率 | 约 100 Hz，但数据包内没有采样率字段 |

### 3.2 字节布局

| 偏移 | 长度 | 类型 | 含义 |
|---:|---:|---|---|
| 0 | 1 | `uint8` | 固定帧头 `0x7D` |
| 1 | 1 | `uint8` | 固件原始字节；当前实机通常恒为 1，不能当作可靠帧序号 |
| 2 | 1 | `uint8` | 固定 `0xF0` |
| 3 | 1 | `uint8` | 固定 `0x02` |
| 4..123 | 120 | 15 × `>hhhh` | 15 个 Hall 通道 |
| 124 | 1 | `uint8` | 保留/语义未公布，不用于控制 |

第 `i` 个通道的 8 bytes 位于 `4 + 8*i`，解码为：

```text
int16_be temperature_x10
int16_be hall_x
int16_be hall_y
int16_be hall_z
```

温度换算为 `temperature_c = temperature_x10 / 10`。Hall 原始数是有符号 int16，主机会按每脚、每点、每轴独立解卷绕为 int32/int64 计数。

已知帧中没有可用的硬件时间戳，也没有已验证的递增设备序号。因此必须保存主机 `CLOCK_MONOTONIC` 接收时间。

### 3.3 实测速率的正确解释

单左脚 15 s 实测为 1499 帧，平均 `99.926 Hz`。本机双脚原始 NPZ 的 65 s 数据也分别约为 `99.88 Hz` 和 `99.85 Hz`。

但 BLE 到达具有抖动和成批到达，不能用“帧数/时长”代替每帧时间戳；必须保存平均速率、P50/P95/最大间隔和长间隔计数。

## 4. 原始采集文件格式

### 4.1 单脚 NPZ

`/home/mosense/guo_1/vola_sensor/record_raw_hall.py` 保存：

| key | shape | dtype | 含义 |
|---|---|---|---|
| `timestamp_s` | `[T]` | `float64` | 主机单调接收时间 |
| `sequence` | `[T]` | `int64` | 主机解析器递增序号 |
| `header_byte_1_u8` | `[T]` | `int16` | 原始帧第 1 字节；可缺省，不当作序号 |
| `hall_xyz` | `[T,15,3]` | `int32` | 解卷绕后的 Hall 原始计数 |
| `temperature_c` | `[T,15]` | `float32` | 摄氏度 |
| `valid` | `[T]` | `bool` | 帧是否通过解码检查 |
| `metadata` | `[K]` | Unicode | 脚号、地址、适配器、单位等 |

注：2026-08-09 早期 NPZ 还没有 `header_byte_1_u8`和适配器元数据，读取程序必须允许这两项缺省。

### 4.2 双脚 `raw_frames.csv`

每条真实 BLE Notify 占一行，左右脚按到达顺序混合记录。前缀字段为：

```text
wall_time_ns, monotonic_ns, monotonic_s,
side, device_name, address, adapter,
source_sequence, sample_period_s, valid, reference_normal_n
```

后续为：

```text
temp_0_x10 ... temp_14_x10
mag_0_x, mag_0_y, mag_0_z ... mag_14_x, mag_14_y, mag_14_z
```

`source_sequence` 目前只是原始帧第 1 字节，实机中通常恒为 1，不能用它检测丢包。丢包/掉频必须用 `monotonic_ns` 的间隔和连接状态判断。`reference_normal_n` 仅是人工施加载荷的实验标签，不是传感器输出，无参考力时应为空。

### 4.3 双脚 `paired_50hz.csv`

该文件在主机统一的 50 Hz 发布时刻保留左右脚快照，Hall 数值不做插值。字段顺序为：

```text
publish_sequence, publish_wall_ns, publish_monotonic_ns,
left_right_frame_skew_ns,

left_valid, left_age_s, left_sample_period_s,
left_frame_wall_ns, left_frame_monotonic_ns, left_source_sequence,
left_P00_temp_x10 ... left_P14_temp_x10,
left_P00_bx, left_P00_by, left_P00_bz ... left_P14_bz,

right_valid, right_age_s, right_sample_period_s,
right_frame_wall_ns, right_frame_monotonic_ns, right_source_sequence,
right_P00_temp_x10 ... right_P14_temp_x10,
right_P00_bx, right_P00_by, right_P00_bz ... right_P14_bz
```

用 `publish_monotonic_ns` 与同一主机的机器人日志对齐。若任一脚 `valid=0`，对应的旧 Hall 数组不得当作新测量。

## 5. 真机实验实时原始包 `F0R1`：936 bytes

`F0R1` 仅用于双脚原始采集和与机器人日志对齐，不直接输入当前策略。默认路径为 `/tmp/g1_foot_hall_capture.bin`。整个包为小端：

| 偏移 | 类型 | 字段 |
|---:|---|---|
| 0 | `uint32` | magic `0x46305231` (`F0R1`) |
| 4 | `uint32` | version = 1 |
| 8 | `uint64` | publish sequence |
| 16 | `int64` | publish wall time ns |
| 24 | `int64` | publish monotonic time ns |
| 32, 40 | 2 × `int64` | left/right frame wall time ns |
| 48, 56 | 2 × `int64` | left/right frame monotonic time ns |
| 64, 68 | 2 × `uint32` | left/right raw header byte 1 |
| 72, 76 | 2 × `uint32` | left/right valid |
| 80, 84 | 2 × `float32` | left/right age s |
| 88, 92 | 2 × `float32` | left/right period s |
| 96 | 90 × `int64` | raw Hall `[2,15,3]` |
| 816 | 30 × `int32` | temperature_x10 `[2,15]` |

## 6. 控制策略实时包 `F0M1`：400 bytes

`F0M1` 是当前 Hall-only 策略真机输入的磁信号边界。默认路径为 `/tmp/g1_foot_rl_obs.bin`，整个包为小端：

| 偏移 | 类型 | 字段 |
|---:|---|---|
| 0 | `uint32` | magic `0x46304D31` (`F0M1`) |
| 4 | `uint32` | 主机发布序号 |
| 8 | `uint64` | 主机 wall timestamp ns |
| 16, 20 | 2 × `float32` | `valid_left, valid_right` |
| 24, 28 | 2 × `float32` | `age_left_s, age_right_s` |
| 32, 36 | 2 × `float32` | `period_left_s, period_right_s` |
| 40 | 90 × `float32` | `magnetic[2,15,3]` |

`magnetic` 不是 Tesla，而是已完成空载基线和温度补偿的无量纲 Hall 响应：

```text
baseline_T = baseline_xyz + (temperature_x10 - T_ref_x10) * temp_coefficient
magnetic_normalized = clip((raw_counts - baseline_T) / scale_xyz, -6, 6)
```

`temperature` 不直接放入 F0M1，只用于发布前补偿。一个可用的归一化文件必须包含左/右脚身份、`baseline_xyz[15,3]`、`scale_xyz[15,3]`、`reference_temperature_x10[15]`和 `temperature_coefficient_per_x10[15,3]`。

任一脚超过 0.20 s 没有新数据时，桥不再发布新的合格对。控制器使用 0.25 s stale 门限；超时后将有效位置零并进入保守/停机路径，不得用旧数据继续高速走。

当前实时桥的轴对齐能力只有：

```text
sensor_permutation[15] + 全局 axis_sign[3]
```

它尚未应用可视化代码中每个芯片各自的 XY 安装旋转。因此，在逐通道三轴标定完成前，F0M1 里的 `Bx/By/Bz` 只能称为“按当前线序归一化后的 XYZ”，不能声称已经是精确的足底 link 局部轴。

## 7. F0M1 如何进入 1864 维策略观测

控制器以 50 Hz 运行，将 F0M1 的当前帧写入 15 帧 Hall 历史。最终 actor 输入必须严格为 1864 维：

| 索引 | 长度 | 内容 |
|---|---:|---|
| `0:15` | 15 | 5 帧 `base_ang_vel[3]` |
| `15:30` | 15 | 5 帧 `projected_gravity[3]` |
| `30:45` | 15 | 5 帧 `command[vx,vy,wz]` |
| `45:190` | 145 | 5 帧 `joint_pos[29]` |
| `190:335` | 145 | 5 帧 `joint_vel[29]` |
| `335:480` | 145 | 5 帧 `last_action[29]` |
| `480:1830` | 1350 | 15 帧 Hall `2×15×3` |
| `1830:1860` | 30 | 15 帧左/右脚实测采样周期 |
| `1860:1862` | 2 | 左/右脚当前有效位 |
| `1862` | 1 | 机体横向速度 `body_vy` |
| `1863` | 1 | 相对目标航向误差 |

Hall 的展平顺序必须是：

```text
[time oldest -> newest,
 foot left -> right,
 point P00 -> P14,
 axis Bx -> By -> Bz]
```

注意：历史配置里最后一项的名字仍可能显示为 `foot_sensor_age_lr`，但当前 1864 维 Motion actor 的 `1862:1864` 实际是 `body_vy` 和 `relative_heading`，不是包年龄。F0M1 的 age 字段用于外部链路健康和安全包络，不得错塞进这两维。

Actor 不包含摩擦系数、接触力、滑移标签或地面分段标签。这些量只能作为仿真 critic/奖励或离线评估真值。

## 8. 为标定和真机训练需要保存什么

### 8.1 必须保存的足底字段

- `hall_raw_counts[T,2,15,3]`；
- `temperature_x10[T,2,15]`；
- `valid_lr[T,2]`、`age_s_lr[T,2]`、`sample_period_s_lr[T,2]`；
- 左右脚各自的帧单调时间、发布单调时间和帧时差；
- 左右脚名称、BLE 地址、适配器地址、通道排列和轴符号；
- 数据文件 SHA256、操作员注释、实验阶段和安全绳状态。

### 8.2 与机器人同步的必须字段

- 时间戳对齐的 `command[vx,vy,wz]`；
- `base_ang_vel[3]`、重力投影/姿态、`body_vy`和航向误差；
- 29 关节位置、29 关节速度和 29 维实际上帧动作；
- episode/session id、安全停机、跌倒和人工中断标记；
- 若有外部高可信滑移真值，必须标注其来源和时间延迟。不得用 Hall 数据自己生成“力/滑移真值”再反过来训练。

### 8.3 建议采集阶段

1. 悬空空载与温漂；
2. 顶置吊架下双足静立与重心转移；
3. 吊架下低速直走；
4. 前掌、中足、后跟的可重复局部加载；
5. 已知方向的剪切、倾斜和卸载回程；
6. 吊架下的 H→L→H 与 L→H→L 地面过渡，多种指令速度。

## 9. 数据质量门槛

正式数据不能只看文件是否成功保存。当前采集程序使用的主要门槛为：

| 指标 | PASS/REVIEW | FAIL |
|---|---|---|
| 单脚原始帧率 | `>=95 Hz` 为 PASS，`80–95 Hz` 为 REVIEW | `<80 Hz` |
| 坏帧 | 0 | `>0` |
| 双脚同时有效率 | `>=95%` | `<95%` |
| 左右帧时差 P95 | `<=20 ms` 为 PASS，`20–50 ms` 为 REVIEW | `>50 ms` |
| 无载线性漂移 P95 | `<=1.2 counts/s` | 超过需 REVIEW/FAIL |
| 无载线性漂移最大值 | `<=2.5 counts/s` | 超过需 REVIEW/FAIL |

### 9.1 当前实测数据状态

2026-08-09 的 120 s “吊架低速直走” session 已正常封存，但不等于质量通过：

- 左脚 `42.966 Hz`，9 次重连；
- 右脚 `99.873 Hz`，0 次重连；
- 就绪后双脚同时有效 `2520 / 5783 = 43.58%`；
- 左右帧时差 P95 约 `26.22 ms`。

因此该 session 只可用于链路故障诊断，不能作为最终归一化、摩擦自适应训练或上机验收数据。必须先解决左脚 BLE 掉频/重连。

截至 2026-08-11 本次核验，未找到已验收的 `normalization/left.json` 和 `normalization/right.json`，实时健康信息也仍显示 `normalized=false`。所以 F0M1 的字节格式已确定，但可用于正式策略的左右脚归一化参数尚未完成。在此之前只能记录 raw counts 或运行显式 `raw-only` 诊断，不得将未标定 raw counts 伪装成正式 F0M1 策略输入。

## 11. 尚未确定、不得臆测的项目

- 已有数据包不包含 Hall 芯片型号，因此不能仅根据协议声称为 `MLX90393`。
- 目前没有已验证的 counts-to-Tesla 系数。
- 目前没有应用于控制输入的 Hall-to-force 映射。
- 左右脚通道 permutation 和 XYZ 轴符号当前仍为临时 identity，最终装配后必须实测确认。
- 可视化中的逐芯片 XY 旋转仍是暂定布线约定，当前真机桥未将其作为已标定参数应用。
- A4 布局的横向正号、右脚镜像规则和足底 link 轴对齐必须通过已知方向的磁体位移实验确认。
- 左右脚归一化 JSON 尚未验收，当前不得将 raw counts 直接作为正式策略输入。
- 仿真内部磁场单位是 Tesla，真机原始单位是 counts，策略 F0M1 单位是无量纲；三者必须在日志中明确标记，不得混用。
